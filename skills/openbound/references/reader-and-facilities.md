# 读者路径、仓库设施与视觉表达

在现有公共入口不能支持目标读者，或补充设施能解决具体问题时读取。先检查已有内容的真实效果，再决定改什么。

## 保留成熟内容，补有因果理由的缺口

不要以文件是否存在衡量完备。README 已让读者理解并运行工具，就保留其结构；测试和 CI 已验证实际交付，就不另建一套；既定许可证有效且范围明确，就不替换它。

| 读者的实际需要 | 合适的工程动作 |
|---|---|
| 判断项目能做什么、有什么限制 | 修正入口说明、真实例子与支持范围；删去过度承诺 |
| 安装/运行现有软件 | 验证公开依赖、配置示例、安装命令和从新根运行的路径 |
| 理解系统或独特机制 | 提供准确解释与必要的架构/流程图；与实现对应 |
| 使用提取的库/API | 给出真实接口例子、错误行为、兼容边界和测试入口 |
| 判断研究构想是否值得进一步讨论 | 说明问题、机制、依据、反例和未解决点；可不提供可执行程序 |
| 提交 bug/贡献 | 写清支持的贡献形式与验证方式；作者不接收贡献时如实说明 |
| 获得新版本或迁移 | 提供与实际变化相称的发布说明与破坏性变更提示 |

小型脚本可以只需要 README 的几段；框架可能需要读者分层、API、示例和 CI。公开但不维护的作品仍应让读者知道当前状态；不必创建空 SECURITY、CONTRIBUTING、CODE_OF_CONDUCT 或 issue 模板来装成熟。

## 说明必须通向真实使用

按读者顺序组织：价值与范围 → 最短有效体验 → 机制与选择 → 深入使用/限制。权威路径可以不同：生成 API 可能由代码权威，README 由作者维护，历史决策有单独记录。不要把所有资料合并成一个庞大 README，也不要为了“单一真源”删除帮助读者的短说明。

实际运行承诺的命令。文件名、包名、路径、环境变量、链接和截图应来自最终候选。配置例子使用可用的无秘密默认值或清楚的必填占位；绝不把真实凭据填进去使 quickstart 看起来成功。

文档与实现矛盾时先确认哪个表达当前作者意图。需要恢复真实行为时，定向检查相关源码、构建和运行证据；不为一次链接修复发起整仓审计。

## CI 与贡献形式

保留项目已有测试入口；CI 应执行同一入口并验证真实公共环境。只添加能捕获当前风险的检查。新项目可用精简 CI；纯文本 Blueprint 可以只做链接/渲染检查，甚至不需要 CI。

检查 fork/PR 上是否会接触秘密、执行未经审查代码、上传私人日志或发布产物。不要为了让外部贡献测试通过而扩大令牌或运行器权限。开源贡献不是所有作品的默认承诺；提交 issue、邮件反馈、讨论、patch 或暂不接受贡献均可。

贡献流程必须说明实际接受的对象和边界。外部 PR 回流私人系统时按 `maintenance.md` 处理，不把公共 CI 通过当作进入私人环境的授权。

## 图应回答一个真实问题

当结构、数据流、状态或信任边界难以从短文理解时，主动考虑图。先列出要表达的节点、关系、来源与读者问题；不先画一张泛化“美观架构图”再填词。

保留可编辑图源，例如 Mermaid、Graphviz、Excalidraw 或项目现用格式。用确定性渲染器渲染实际图源，检查最终尺寸、文本截断、箭头方向、交叉、图例与暗/亮背景可读性。源语法合法不等于布局经过验证；只渲染而未目视检查时这样报告。

架构图标注已实现与设想部分、方向与边界，使关系准确。控制同一视图的对象数；必要时用总览加局部图，而非缩小字号塞满画布。文字提供图的要点或等价结构说明，颜色不独自承载含义，给导出图合适替代文本。

从私人系统制作图时，先选允许公开的事实再重建。检查源文件、SVG 文本/元数据、嵌入对象、注释、外链、字体与导出文件；仅遮挡标签或裁切截图可能仍保留敏感数据。图也可能暴露拓扑与身份组合，按实际威胁审查。

## 完成并返回

交付所需设施的实际内容与验证结果，指出保留了哪些成熟入口及为什么新增特定内容。不把“建议添加 README/CI/图”当作完成。若受权限或缺失环境阻碍，先做好可审查版本并精确标记未验证部分。
